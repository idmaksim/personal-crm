# Личная CRM

Приложение для ведения контактов людей, которых вы знаете лично: кто это, откуда
знакомы, телефон и почта, и заметки о том, о чём договорились. Продуктовая идея —
в `specs/01-продуктовая-идея.md`.

## Что внутри

- **Next.js (App Router) + TypeScript** — страницы и серверный код
- **React + Tailwind CSS + shadcn/ui** — интерфейс
- **PostgreSQL + Drizzle** — база данных, схема и миграции в коде
- **Better Auth** — вход по ссылке из письма (magic link), без паролей
- **Docker** — локально поднимает Postgres, Adminer (просмотр базы) и Mailpit
  (почтовая заглушка)

Данные читаются и пишутся только на сервере. Браузер к базе напрямую не обращается.
Каждый пользователь видит и меняет только свои контакты, заметки и группы.

## Вход

Входа по паролю нет — только по ссылке из письма:

1. На странице `/login` вводите почту и нажимаете «Получить ссылку».
2. Приходит письмо со ссылкой; она действует 15 минут и один раз. Новая
   ссылка гасит все предыдущие, неиспользованные.
3. Переход по ссылке вводит в приложение. Если почта новая — заводится новый
   пользователь (отдельной формы регистрации и имени нет).
4. Вход держится 30 дней с последнего захода на этом устройстве; можно быть
   внутри сразу с нескольких устройств. «Выйти» в шапке завершает сессию
   только на этом устройстве.

Локально и в автотестах письма идут не наружу, а в заглушку **Mailpit** —
открыть <http://localhost:8025> и забрать ссылку оттуда. На сервере та же
отправка идёт через Resend.

## Как запустить

Нужны установленные **Docker**, **Node.js** и **pnpm**.

1. Создайте файл `.env` по образцу `.env.example` и заполните значения:
   - параметры Postgres (пользователь, пароль, имя базы, порт, `DATABASE_URL`);
   - `BETTER_AUTH_SECRET` — случайная строка, например `openssl rand -base64 32`;
   - `BETTER_AUTH_URL=http://localhost:3000`;
   - `SMTP_HOST=localhost`, `SMTP_PORT=1025`, `SMTP_SECURE=false`, `SMTP_USER`
     и `SMTP_PASS` оставьте пустыми, `MAIL_FROM` — любой адрес вида
     `noreply@mail.crm.localhost` (письма всё равно идут в Mailpit, не наружу);
   - `OWNER_EMAIL` — ваша почта. Миграция сделает владельцем именно этой
     почты все контакты, заметки и группы, что уже есть в базе (включая
     демо-данные `db:seed`) — без этого ключа `db:migrate` и `db:seed`
     откажутся работать.
   - `RESEND_API_KEY` локально не нужен — он только для сервера.

2. Поднимите базу данных и почтовую заглушку:

   ```bash
   docker compose up -d postgres mailpit
   ```

3. Установите зависимости:

   ```bash
   pnpm install
   ```

4. Примените миграции (создаст таблицы, включая таблицу-владельца `OWNER_EMAIL`):

   ```bash
   pnpm db:migrate
   ```

5. (По желанию) наполните базу тестовыми данными — 1000 контактов владельца
   `OWNER_EMAIL`:

   ```bash
   pnpm db:seed
   ```

6. Запустите приложение:

   ```bash
   pnpm dev
   ```

   Откройте <http://localhost:3000> — приложение откроет страницу входа.
   Введите почту, заберите ссылку из Mailpit (<http://localhost:8025>) и
   перейдите по ней.

## Полезные команды

| Команда            | Что делает                                       |
| ------------------ | ------------------------------------------------ |
| `pnpm dev`         | Запуск в режиме разработки                       |
| `pnpm build`       | Сборка production-версии                         |
| `pnpm start`       | Запуск собранной версии                          |
| `pnpm db:generate` | Сгенерировать SQL-миграцию из изменений схемы    |
| `pnpm db:migrate`  | Применить миграции к базе                        |
| `pnpm db:seed`     | Залить 1000 тестовых контактов (очищает таблицы) |

Просмотреть базу вручную можно через Adminer на <http://localhost:8080>
(сервер `postgres`, данные для входа — из `.env`).

## Выкатка и откат (прод)

Как всё устроено:

- **Pull request** → автоматически гоняется CI (линт, формат, типы, тесты, сборка
  образа). Красный CI в `main` не вливается.
- **Merge в `main`** → собирается образ и выкатывается **только тест-стенд**
  (`test-app.dobrymaxx.ru`), который пересевается свежей копией данных прода. Прод
  при merge **не трогается** — это место проверить новый код перед продом.
- **Прод** выкатывается только вручную, кнопкой (см. ниже). Заодно каждый merge
  подчищает старые версии образа в GHCR (остаются последние).

### Как выкатить прод

1. GitHub → вкладка **Actions** → слева workflow **Deploy prod** → кнопка **Run
   workflow**, ветка `main` → **Run workflow**.
2. Workflow соберёт текущий `main`, **сделает бэкап базы**, применит миграции,
   поднимет новый образ и прогонит smoke-проверку `/health` (локально и через
   `app.dobrymaxx.ru`). Он же устанавливает/обновляет суточный таймер бэкапа.
3. Зелёный прогон = выкатка прошла. Проверьте руками: откройте `app.dobrymaxx.ru`.
4. Красный smoke = выкатка упала и сама ничего не откатывает — см. «Как откатить».

### Как откатить

Откат ручной, на сервере (автоотката нет, по задумке). Два случая:

- **Вернуть прошлую версию кода** (новая выкатка плохая, но база цела):

  ```bash
  bash ~/deploy/deploy.sh ghcr.io/idmaksim/personal-crm:<прошлый-sha>
  ```

  Прошлые SHA — в истории коммитов `main` и во вкладке Packages. Важно: миграции
  «вперёд-только». Если релиз менял схему базы, отката одного образа мало — нужен
  следующий случай.

- **Полный откат (код + данные)** — восстановить базу из бэкапа, снятого **перед**
  плохой выкаткой, и поднять ту версию образа:
  1. `bash ~/deploy/restore.sh ~/deploy/backups/backup_<...>.dump` — вернёт базу
     (спросит `yes`, снимет страховочную копию, поднимет приложение той же версии,
     что работала). Подробнее — в разделе ниже.
  2. При необходимости докатите нужный образ командой `deploy.sh` из первого случая.

## Бэкапы и восстановление (прод)

База прода бэкапится в двух случаях: **раз в сутки** (таймер systemd
`crm-backup` на сервере, в 03:00) и **первым шагом каждой прод-выкатки** — до
того, как миграции тронут данные. Бэкапы лежат на сервере в `~/deploy/backups/`
в файлах вида `backup_<дата-время>_<версия>.dump`. Версия в имени — та, что
работала на момент бэкапа, чтобы было видно, к какому релизу относятся данные.
Хранятся 14 последних бэкапов, старые удаляются автоматически.

Проверить таймер и посмотреть журнал бэкапов на сервере:

```bash
systemctl list-timers crm-backup.timer   # когда следующий запуск
journalctl -u crm-backup                 # что было при запусках
sudo systemctl start crm-backup.service  # снять бэкап прямо сейчас
```

### Как восстановить базу из бэкапа

Восстановление запускается **вручную на сервере** (сам по себе процесс ничего
не восстанавливает и ничего не откатывает). Команда:

```bash
bash ~/deploy/restore.sh ~/deploy/backups/backup_<...>.dump
```

Что делает скрипт по шагам:

1. Показывает, какой файл загрузит и какую базу заменит, и ждёт, пока вы
   введёте `yes`. Любой другой ввод — выход, ничего не меняется.
2. Снимает страховочную копию текущей базы (файл `pre-restore_<...>.dump` там же
   в `backups/`) — на случай, если восстановление нужно отменить.
3. Останавливает приложение, удаляет базу, создаёт её заново пустой и загружает
   бэкап.
4. Поднимает приложение на **той же версии**, что работала до восстановления, —
   версию приложения скрипт не меняет.

Если загрузка бэкапа упадёт, приложение останется остановленным, а путь к
страховочной копии будет в выводе — откат делаете вручную.

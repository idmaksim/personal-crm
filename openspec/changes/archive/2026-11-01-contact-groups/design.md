# Design

## Context

Мотивация — в `proposal.md` (раздел «Why»). Что уже есть в коде и формирует подход:

- Схема (`src/db/schema.ts`): таблицы `contacts` и `notes` на Drizzle, связь
  «контакт → заметки» через внешний ключ с `onDelete: "cascade"`.
- Серверные действия (`src/app/actions.ts`): `"use server"`-функции с паттерном
  `useActionState` (возвращают `{ error }`/`{ message }`), доступ к базе только с
  сервера, аккуратное логирование ошибок без персональных данных (`logDbError`),
  обновление кэша через `revalidatePath`.
- Поиск на главной (`src/app/page.tsx`): сопоставление без учёта регистра и с
  приравниванием «е»/«ё» через `translate(lower(x), 'ё', 'е')`. Страницы помечены
  `export const dynamic = "force-dynamic"`.
- Поля-выборы сделаны нативным `<select>` (`frequency-select.tsx`) — без лишних
  зависимостей. Подтверждение необратимого действия — через готовый
  `alert-dialog` (`delete-contact-button.tsx`).

## Goals / Non-Goals

**Goals:**

- Хранить группы и их связь с контактами с целостностью на уровне базы.
- Единообразно создавать группу «на лету» и из карточки, и из формы добавления.
- Фильтр по группе на главной, совместимый с существующими поиском и пагинацией.
- Переиспользовать сложившиеся паттерны (нативный select, alert-dialog,
  `logDbError`, `revalidatePath`), не добавляя внешних библиотек.

**Non-Goals:**

- Цвета/иконки групп, вложенные группы, сортировка списка по группам.
- Массовые действия над группой (например, «связаться со всеми») — задел на потом.
- Поиск внутри выбора групп (при личном масштабе список групп невелик).
- Автотесты и CI в рамках этой фичи (отложено по решению владельца).

## Decisions

### Модель данных: отдельная таблица + связующая

- `groups`: `id serial PK`, `name text NOT NULL`, `created_at timestamptz`.
- `contact_groups`: `contact_id` → `contacts.id` (`onDelete: cascade`),
  `group_id` → `groups.id` (`onDelete: cascade`), составной первичный ключ
  `(contact_id, group_id)`, индекс по `group_id` для фильтра.
- Каскады дают поведение из спеки: удалили контакт — его связи уходят, группы
  живут; удалили группу — связи уходят, контакты живут.

Альтернатива — массив названий в поле `contacts` — отклонена: нет ссылочной
целостности, тяжело переименовывать и фильтровать.

### Уникальность и нормализация имени

- Имя при сохранении обрезается по краям (`trim`). Уникальность — без учёта
  регистра и различия «е»/«ё», тем же приёмом `translate(lower(name), 'ё', 'е')`,
  что и поиск.
- Гарантия на уровне базы — функциональный уникальный индекс по
  `translate(lower(name), 'ё', 'е')`. Действие дополнительно проверяет совпадение,
  чтобы показать понятное сообщение вместо «сырой» ошибки базы.
- Создание и назначение — по принципу «найти или создать»: ищем группу по
  нормализованному имени, при отсутствии создаём; затем связываем с контактом.
  Операцию оборачиваем в транзакцию; уникальный индекс защищает от гонок.

Альтернатива — тип `citext` — отклонена: тянет расширение Postgres ради одного поля.

### Создание «на лету» и форма добавления

- Единый клиентский компонент выбора групп: показывает уже назначенные группы
  чипами (с «×» для снятия) и поле ввода, которое предлагает существующие группы
  и позволяет ввести новое имя.
- В **карточке** компонент работает с уже существующим контактом: добавление/
  снятие — отдельные серверные действия, список групп приходит с сервера.
- В **форме добавления** контакта ещё нет: выбранные группы набираются на клиенте
  и уходят вместе с формой; `createContact` в одной транзакции создаёт недостающие
  группы («найти или создать») и привязывает их к новому контакту.

### Фильтр по группам на главной

- В URL несколько значений `group` (повторяемый параметр): `?group=3&group=5`
  рядом с `q` и `page`. Фильтр по `id`, а не по имени — ссылка не ломается при
  переименовании группы.
- Семантика — пересечение: показываем контакты, входящие во все выбранные группы.
  В запросе — соединение с `contact_groups` с условием `group_id IN (выбранные)`,
  группировка по контакту и `HAVING count(distinct group_id) = число выбранных`.
  Условие поиска по имени применяется поверх, как сейчас.
- Выбор группы — переключатель (добавить/убрать из набора); `buildHref` переносит
  все выбранные `group` вместе с `q`/`page`, чтобы набор сохранялся при листании.
- Неизвестные/удалённые `group` id отбрасываются: фильтруем по оставшимся, а если
  не осталось ни одного — показываем весь список.

Альтернатива — фильтр по одной группе — отклонена по просьбе владельца; AND вместо
OR выбран им же (нужны те, кто сразу во всех отмеченных группах).

### Управление группами (создание, переименование, удаление) — на странице `/groups`

- Группу можно создать «на лету» у контакта, а также явно на странице `/groups`
  (поле «новая группа», та же логика «найти-или-создать»). Переименование и
  удаление — глобальные операции над группой, поэтому им тоже нужен свой дом. Это
  отдельная страница `/groups` со списком всех групп: создание, переименование
  (инлайн-форма) и удаление (кнопка с `alert-dialog`-подтверждением, как у удаления
  контакта).
- Альтернатива — встроить управление прямо в чипы фильтра на главной — отклонена:
  засоряет главную и делает подтверждение удаления неудобным.
- Фильтр групп на главной ведёт ссылкой на `/groups` для управления.

> Это решение по интерфейсу: если владелец захочет управление не на отдельной
> странице, а, например, прямо в фильтре — поправим, оно затрагивает только
> раздел управления.

### Серверные действия (в `src/app/actions.ts`)

- `addGroupToContact(contactId, name)` — найти-или-создать по имени + связать.
- `createGroup(name)` — создать группу на странице `/groups` (найти-или-создать по
  нормализованному имени, без привязки к контакту).
- `removeGroupFromContact(contactId, groupId)` — снять связь.
- `renameGroup(groupId, name)` — переименовать с проверкой уникальности.
- `deleteGroup(groupId)` — удалить (связи уходят каскадом).
- `createContact` расширяется приёмом списка выбранных групп.
- Все — в стиле текущих действий: `logDbError` без утечки имён в логи,
  `revalidatePath("/")`, `revalidatePath("/groups")` и затронутых карточек.

## Risks / Trade-offs

- [Проверка уникальности в действии и функциональный индекс могут разойтись] →
  держим нормализацию в одном SQL-помощнике и используем его в обоих местах.
- [Свободный ввод имени плодит почти-дубли (опечатки, разный внутренний пробел)] →
  `trim` + приведение регистра/«ё»; опечатки — на усмотрение владельца, он может
  переименовать или удалить группу.
- [Гонка при одновременном создании одноимённой группы] → операция в транзакции,
  финальная защита — уникальный индекс (повтор перехватываем как «найти»).
- [Удаление одной из выбранных в фильтре групп] → отсутствующие id отбрасываются,
  фильтруем по оставшимся; не осталось ни одного — весь список, страница не падает.

## Migration Plan

- Миграция Drizzle добавляет таблицы `groups` и `contact_groups` (с индексами и
  внешними ключами). Генерируем `pnpm db:generate`, применяем отдельным шагом до
  старта нового образа (как заведено в проекте). Бэкфилл не нужен — фича новая.
- Откат — вручную: удалить две новые таблицы. Контакты и заметки при этом не
  затрагиваются.

## Open Questions

- Нужен ли поиск/фильтрация внутри выбора групп, когда групп станет много. Можно
  добавить позже, не меняя модель данных и остальной подход.

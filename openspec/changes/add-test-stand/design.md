# Design

## Context

Мотивация — см. proposal.md («Why»). Текущее состояние:

- Прод — один compose-проект `prod` на сервере: контейнеры `prod-app`,
  `prod-postgres`, порт `127.0.0.1:3000`, том `prod_postgres_data`. Секреты в
  `~/deploy/.env` (не в git).
- `deploy/deploy.sh` зашит под прод: `docker compose -p prod`, контейнер
  `prod-postgres`, всегда делает бэкап, миграции, smoke на `127.0.0.1:3000`.
- `.github/workflows/deploy.yml` на push в `main` собирает образ и одним шагом
  копирует `deploy/` на сервер и запускает `deploy.sh`. Группа параллельности
  `deploy-main`, `cancel-in-progress: false` (деплои уже выстроены в очередь).
- nginx для `app.dobrymaxx.ru` правится на сервере руками; сертификат общий с
  лендингом (`live/dobrymaxx.ru`).
- Авторизация: ссылка входа строится Better Auth из `baseURL = BETTER_AUTH_URL`;
  кука сессии по умолчанию host-only (без атрибута `Domain`). Общий домен для куки
  нигде не включён (нет `crossSubDomainCookies`).

## Goals / Non-Goals

**Goals:**

- Второе окружение (`test`) на том же сервере, максимально переиспользуя прод-скрипт
  и compose; прод-путь не меняется (те же имена контейнеров, порт, бэкап).
- Параметризация окружением в одном месте (`deploy.sh`), а не копией скриптов.
- Изоляция данных и ресурсов стенда; данные — свежая копия прода на каждой выкатке.

**Non-Goals:**

- Не меняем механику выкатки прода и его бэкапов/отката.
- Не добавляем автотестов (инфраструктура проверяется выкаткой и руками — правило
  проекта).
- Не трогаем чужие конфиги nginx и общий сертификат.

## Decisions

### 1. Один compose-файл, параметризованный окружением

`docker-compose.prod.yml` параметризуем переменными с прод-значениями по умолчанию,
чтобы прод-путь остался байт-в-байт прежним, а стенд задавался другими значениями:

- `container_name: ${APP_CONTAINER:-prod-app}` и `${DB_CONTAINER:-prod-postgres}`.
- Порт: `"127.0.0.1:${APP_PORT:-3000}:3000"`.
- Файл настроек: `env_file: ${ENV_FILE:-.env}`.
- Лимиты памяти: `mem_limit: ${APP_MEM_LIMIT:-0}` / `${DB_MEM_LIMIT:-0}` (`0` =
  без лимита, так остаётся у прода).

Изоляция тома — через имя проекта: том `postgres_data` под проектом `prod`
становится `prod_postgres_data`, под `test` — `test_postgres_data`. Отдельный
compose-файл для стенда не заводим (дублирование), всё различие — в значениях
переменных, которые задаёт `deploy.sh`.

_Альтернатива:_ отдельный `docker-compose.staging.yml` — отвергнуто: дублирует
описание сервисов, расходится с продом при правках.

### 2. `deploy.sh <image> [env]` — ветвление по окружению

Второй аргумент `env` (по умолчанию `prod`) задаёт набор значений:

| параметр        | prod            | test (стенд)         |
|-----------------|-----------------|----------------------|
| проект compose  | `prod`          | `test`               |
| контейнеры      | `prod-app/‑postgres` | `test-app/‑postgres` |
| порт            | `3000`          | `3100`               |
| файл настроек   | `.env`          | `.env.staging`       |
| бэкап базы      | да              | нет                  |
| пересев из прода| нет             | да                   |
| лимиты памяти   | нет             | да                   |

Прод-ветка кода скрипта не меняется по смыслу — значения по умолчанию
воспроизводят нынешнее поведение. Smoke `/health` бьёт по `127.0.0.1:${APP_PORT}`
(минуя nginx и его пароль).

### 3. Пересев данных стенда из прода (только `env=test`)

Перед миграциями стенда: берём дамп прод-базы прямо из контейнера `prod-postgres`
и восстанавливаем в базу стенда с пересозданием объектов:

```
docker exec prod-postgres pg_dump -U <prod_user> -d <prod_db> -Fc \
  | docker exec -i test-postgres pg_restore --clean --if-exists --no-owner \
      -U <test_user> -d <test_db>
```

- `--no-owner` — у стенда свой пользователь базы, владельца не переносим.
- `--clean --if-exists` — чистит прежние объекты стенда (пересев), первый пустой
  стенд тоже наполняется.
- Дамп `pg_dump` консистентен даже на работающем проде (снимок на один момент).
- Прод-креды берём из окружения контейнера `prod-postgres` (как и бэкап сейчас),
  скрипт их не читает из файлов.

После пересева запускаем миграции стенда — они идемпотентны (журнал миграций
пришёл из прода; прод выкачен раньше, значит схема уже на нужной версии).

### 4. Workflow: прод первым, стенд после, прод независим

Разбиваем `deploy.yml` на задачи:

- `build` — собирает и пушит образ, отдаёт ссылку на образ.
- `deploy-prod` — `needs: build`, выкатывает прод тем же шагом, что сейчас:
  `deploy.sh <image>` (без второго аргумента = прод).
- `deploy-staging` — `needs: [build, deploy-prod]`, выкатывает стенд:
  `deploy.sh <image> staging`.

Так прод катится первым и не зависит от исхода стенда (стенд ниже по графу: упал
стенд — прод уже зелёный). Группу параллельности оставляем на весь workflow
(`cancel-in-progress: false`): следующий merge ждёт, пока текущий прогон (прод +
стенд) полностью завершится, — две выкатки на стенд не пересекаются (п.6).

_Альтернатива:_ отдельный workflow на стенд — отвергнуто: разъедется порядок и
общая очередь прод↔стенд, появится риск пересева стенда из непромигрированного
прода.

### 5. nginx стенда: свой конфиг, пароль, свой сертификат

Новый файл в репозитории `deploy/nginx/test-app.dobrymaxx.ru.conf` (источник правды,
применяется на сервере руками, как прод-конфиг):

- `server_name test-app.dobrymaxx.ru;` → `proxy_pass http://127.0.0.1:3100;`.
- `auth_basic "..."; auth_basic_user_file /etc/nginx/.htpasswd-test-app;` — пароль.
- `location = /health { auth_basic off; proxy_pass ...; }` — `/health` без пароля,
  чтобы публичный smoke и мониторинг работали (статус не раскрывает данных).
- Свой сертификат `live/test-app.dobrymaxx.ru` (отдельный certbot `-d
  test-app.dobrymaxx.ru`), общий серт прода/лендинга не трогаем.

`.htpasswd-test-app` создаётся на сервере командой владельца (пароль — секрет, в git
не хранится).

### 6. Авторизация: ссылка и кука — конфигом, кода не меняем

- Ссылка (п.3 спеки): Better Auth строит URL из `BETTER_AUTH_URL`; у стенда в
  `.env.staging` он `https://test-app.dobrymaxx.ru`, у прода — прод-адрес. Значит
  ссылка уже ведёт на своё окружение. Правок кода не требуется — только проверяем
  и фиксируем, что ничего не переопределяет базовый URL на запрос.
- Кука (п.4 спеки): host-only по умолчанию, общий домен не включён. Правок не
  вносим; задача — подтвердить и не добавить ничего, что расширит куку на домен.

### 7. Настройки стенда (`~/deploy/.env.staging`, только на сервере)

Свои: `POSTGRES_*`, `DATABASE_URL` (хост `postgres` — резолвится внутри сети
проекта `test`), `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL = PUBLIC_APP_URL =
https://test-app.dobrymaxx.ru`. Общие с продом: отправка писем через Resend
(входные письма реальные — уходят только тому, кто запросил вход), `OWNER_EMAIL`.
В репозиторий кладём обновлённый `deploy/.env.example` с пояснением про стенд; сам
`.env.staging` создаёт владелец (секреты не в git).

## Risks / Trade-offs

- **Пересев грузит прод-базу на каждой выкатке** → для личной CRM дамп маленький и
  идёт после выкатки прода; при росте данных можно перейти на пересев по команде.
- **На стенде лежат реальные данные прода** → закрыто паролем (basic auth) + HTTPS
  + host-only кукой; `/health` открыт, но данных не отдаёт.
- **Два Postgres и два app на одном сервере — память/диск** → лимиты памяти у
  стенда (прод без лимита), лог-файлы ограничены по размеру (уже есть), старые
  образы подчищаются (уже есть).
- **Параметризация compose не должна сдвинуть прод** → все дефолты переменных
  воспроизводят текущие имена/порт/поведение; проверяем первой же прод-выкаткой.
- **Пароль ломает smoke стенда** → `/health` выведен из-под basic auth; локальный
  smoke и так идёт по `127.0.0.1:3100`.
- **Откат стенда** → стенд одноразовый, авто-отката нет; при сбое — чиним вперёд
  или повторяем выкатку, прод не затронут и откатывается как раньше (вручную).

## Open Questions

  переменных).

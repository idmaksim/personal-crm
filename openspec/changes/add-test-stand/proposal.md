# Proposal

## Why

Сейчас у приложения одно окружение — прод. Проверять доработки перед выкаткой
негде: любая ошибка видна сразу живым пользователем на реальных данных. Нужен
тест-стенд (staging — отдельная копия приложения для проверок) на том же сервере:
отдельный адрес `test-app.<домен>`, свои данные-копия прода, закрытый паролем, —
чтобы прогонять изменения на почти-боевых условиях, ничего не задев в проде.

## What Changes

- Появляется второе окружение — тест-стенд на адресе `test-app.<домен>`, на том же
  сервере, что и прод. У стенда своя база, свой файл настроек (`.env`) и лимиты
  памяти у контейнеров, чтобы стенд не мешал проду.
- Данные стенда — копия прода: при каждой выкатке стенд пересоздаёт свою базу из
  свежего бэкапа прода. Любые правки данных на стенде живут только до следующей
  выкатки.
- Один скрипт выкатки обслуживает оба окружения: окружение задаётся параметром.
  Для стенда бэкап базы не делается (данные одноразовые).
- Выкатка на стенд идёт по тому же событию, что и прод, — merge в `main`. Порядок:
  **сначала прод** (бэкап → миграции → проверка `/health`), **потом стенд** (копия
  свежего прода → миграции → старт → проверка). Прод выкатывается как раньше и не
  зависит от исхода выкатки стенда.
- Два деплоя на один стенд одновременно не идут — выкатки стенда выстроены в
  очередь.
- Тестовый домен закрыт паролем на уровне nginx (basic auth, один общий пароль) и
  получает отдельный TLS-сертификат (выпускаем через certbot, чужой общий серт не
  трогаем).
- Ссылка во входном письме ведёт на адрес того окружения, где запросили вход
  (вошёл на стенде — ссылка на стенд, на проде — на прод). Кука входа живёт только
  на своём поддомене и не распространяется на общий домен — вход на стенде и на
  проде независимы.

Автотестов для этой доработки не добавляем: сервер, скрипты выкатки и nginx
проверяются настоящей выкаткой и руками (это уже правило проекта).

## Capabilities

### New Capabilities

- `test-stand`: тест-стенд как отдельное окружение рядом с продом — его изоляция
  (своя база, настройки, лимиты памяти), пересев данных из прода при каждой
  выкатке, единый параметризуемый скрипт выкатки, порядок и очередь выкаток,
  закрытие домена паролем и свой TLS-сертификат.

### Modified Capabilities

- `user-auth`: вход становится безопасным для нескольких окружений — ссылка в
  письме ведёт на то окружение, где запросили вход, а кука входа ограничена своим
  поддоменом и не общим доменом.

## Impact

- **Выкатка**: `deploy/deploy.sh` (параметр окружения, ветка «без бэкапа + пересев
  из прода» для стенда), `deploy/docker-compose.prod.yml` или новый
  compose-файл/оверлей для стенда (свои имена контейнеров, свой том, порт,
  лимиты памяти), `deploy/.env.example` (пример настроек стенда),
  `.github/workflows/deploy.yml` (второй шаг выкатки на стенд после прода, своя
  группа параллельности).
- **nginx/TLS**: новый конфиг `deploy/nginx/test-app.<домен>.conf` с basic auth и
  отдельным сертификатом; общий конфиг и серт прода не меняем.
- **Авторизация**: проверяем и фиксируем, что ссылка строится из адреса окружения
  (`BETTER_AUTH_URL` своего `.env`), а кука остаётся host-only; при необходимости
  правим `src/lib/auth.ts`.
- **Сервер (разово, человек/агент)**: DNS-запись `test-app` добавляет владелец;
  создание `.env` стенда, htpasswd с паролем владельца, выпуск сертификата.
- **Прод**: поведение выкатки прода не меняется.

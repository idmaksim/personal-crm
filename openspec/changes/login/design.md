# Design

## Context

Мотивация — в `proposal.md` (раздел «Why»). Требования — в
`specs/user-auth/spec.md` и `specs/contact-groups/spec.md`. Что уже есть в коде и
формирует подход:

- **Данных-владельца пока нет.** Схема (`src/db/schema.ts`): `contacts`, `notes`,
  `groups`, `contact_groups` — ни у кого нет владельца, все запросы читают всю
  базу. Группы уникальны глобально (функциональный индекс по
  `translate(lower(name),'ё','е')`).
- **Серверные действия** (`src/app/actions.ts`) — `"use server"` функции в стиле
  `useActionState` (`{ error }`/`{ message }`), доступ к базе только с сервера,
  `logDbError` без утечки персональных данных, `revalidatePath`.
- **Страницы** (`src/app/page.tsx`, `contacts/[id]/page.tsx`, `groups/page.tsx`)
  помечены `export const dynamic = "force-dynamic"`, читают базу напрямую.
- **Инфраструктура.** Локально Docker поднимает только Postgres (+ Adminer);
  **Mailpit пока нет**. Выкатка: бэкап → миграции отдельным one-shot
  (`docker compose run --rm migrate`, запускает `node src/db/migrate.mjs`) →
  новый образ → smoke `/health`. e2e в CI идут на настоящий Postgres-сервис,
  Playwright сам собирает и поднимает прод-сервер.
- **История проекта:** были проблемы с cross-origin при заходе по IP (см. PR #11)
  — значит базовый URL аутентификации нужно брать из настройки, а не угадывать.

Проверенные актуальные версии (совместимы со стеком Next 16 / React 19 /
drizzle-orm 0.45.4 / drizzle-kit 0.31.5): `better-auth@1.7.18`,
`nodemailer@10.3.1`, `@types/nodemailer@8.0.2`. Отдельный пакет Resend не нужен —
Resend умеет SMTP, поэтому отправка везде идёт через Nodemailer.

## Goals / Non-Goals

**Goals:**

- Вход по ссылке из письма на Better Auth (MagicLink) с одноразовой ссылкой на 15
  минут и серверной проверкой почты.
- Одна библиотека отправки (Nodemailer), выбор «заглушка/Resend» — настройкой, а
  не кодом; одна сборка работает локально, в CI и на сервере.
- Владелец у контактов и групп; каждый запрос и каждое действие — строго в
  границах текущего пользователя, с проверкой на сервере.
- Разовый перенос существующих данных и демо-данных на владельца `OWNER_EMAIL` без
  потери записей, применяемый шагом миграции на выкатке.
- Автотест изоляции A/B и вход-помощник для автотеста главного сценария.

**Non-Goals (на уровне дизайна):**

- Смена почты, список/отзыв чужих сессий, «запомнить устройство» сверх 30 дней.
- Экран управления пользователями, любые роли.
- Переиспользование лимита писем как общей защиты от спама API (берём только
  правило «3 письма на почту за 10 минут» из требований).

## Decisions

### Better Auth + MagicLink + адаптер Drizzle

- Конфигурация в `src/lib/auth.ts`: `betterAuth({ database: drizzleAdapter(db,
  { provider: "pg" }), plugins: [magicLink({ ... })] })`. Таблицы Better Auth
  (`user`, `session`, `account`, `verification`) генерируем CLI Better Auth, затем
  заводим их в `src/db/schema.ts`, чтобы единым источником схемы оставался код и
  работал `drizzle-kit generate`.
- HTTP-обработчик — `src/app/api/auth/[...all]/route.ts` (хендлер Better Auth).
- Клиент — `src/lib/auth-client.ts` с `magicLinkClient()`; вход на странице входа
  через `authClient.signIn.magicLink({ email })`.
- Альтернатива (свой код токенов и сессий) отклонена: требование прямо называет
  Better Auth/MagicLink, а свой код повторил бы его хуже.

### Одна отправка писем, получатель — настройкой

- Модуль `src/lib/mailer.ts` создаёт один транспорт Nodemailer по настройкам
  окружения и шлёт письмо. Выбор получателя — через переменные, не через код:
  - **Локально и в CI:** SMTP Mailpit (`SMTP_HOST=localhost`, `SMTP_PORT=1025`,
    без авторизации и TLS).
  - **На сервере:** SMTP Resend (`SMTP_HOST=smtp.resend.com`, `SMTP_PORT=465`,
    `secure=true`, пользователь `resend`, пароль — `RESEND_API_KEY`).
- `sendMagicLink` в конфиге Better Auth формирует письмо (отправитель «Личная
  CRM» `<MAIL_FROM>`, тема «Вход в Личную CRM», HTML с кнопкой «Войти», текст про
  15 минут и про игнор) и зовёт `mailer`.
- Так одна и та же сборка образа работает везде — различаются только значения
  `.env`. Альтернатива (SDK Resend на сервере + SMTP локально) отклонена: это уже
  две разные ветки кода, против требования «решают настройки, не код».

### Срок 15 минут, одноразовость, гашение старых ссылок

- `magicLink({ expiresIn: 900 })` — 15 минут. Одноразовость у плагина по
  умолчанию (после перехода токен недействителен). Точное поведение `expiresIn`
  зависит от версии — при реализации проверяем на закреплённой `1.7.18`, что срок
  действительно 15 минут и повтор не входит.
- «Новая ссылка гасит старые» в плагине из коробки не гарантировано, поэтому в
  `sendMagicLink` перед выдачей новой ссылки удаляем прежние невостребованные
  записи `verification` для этой почты.

### Лимит «3 письма на почту за 10 минут»

- Встроенный лимитер Better Auth — по endpoint/IP (по умолчанию 5/60с), это не
  «на почту». Оставляем его грубой защитой, а правило из требований реализуем явно:
  перед отправкой считаем число запросов ссылки по этой почте за последние 10
  минут; если их уже 3 — возвращаем «Слишком часто, попробуй через несколько
  минут» и письмо не шлём.
- Счёт ведём по строкам `verification`, созданным для этой почты за окно (или по
  отдельной небольшой таблице-журналу, если так окажется надёжнее при реализации).
  Это единственное сообщение-исключение из правила «не выдаём, есть ли
  пользователь».

### Сессия 30 дней от последней активности, несколько устройств

- `session: { expiresIn: 60*60*24*30, updateAge: 60*60*24 }` — срок 30 дней,
  продление не чаще раза в сутки при активности. Сессии Better Auth отдельные на
  устройство, поэтому вход с нескольких устройств работает сам собой.
- «Выйти» → `authClient.signOut()` завершает только текущую сессию (это устройство),
  остальные живут.

### Нормализация и серверная проверка почты

- Единый помощник: `trim` + нижний регистр + проверка формата. Применяется и в
  серверном действии запроса ссылки, и внутри обработчика, чтобы проверка
  срабатывала даже на запрос в обход формы (требование «сервер проверяет так же»).
- Неверная почта → ошибка `«Проверь адрес почты»` под полем, письмо не уходит.

### Доступ: единая проверка пользователя на сервере

- Помощник `requireUser()` (`src/lib/session.ts`) читает сессию
  (`auth.api.getSession({ headers })`); нет сессии — `redirect("/login")`; есть —
  возвращает `user`. Используется и в страницах (чтение), и в действиях (запись).
- `middleware.ts` перенаправляет гостя с внутренних адресов на `/login` (быстрый
  заслон). Но главная защита — серверная: каждый запрос и действие фильтруют и
  пишут по `user.id`; спрятанная кнопка защитой не считается.
- Публичны только: страница входа и её ответы, API-маршрут Better Auth и
  `/health` (его дёргает smoke-тест выкатки).

### Владелец у данных и доступ только к своему

- `contacts.owner_id` и `groups.owner_id` — `text`, внешний ключ на `user.id`
  (`onDelete: cascade` — удалили пользователя, ушли его данные). Заметки
  принадлежат владельцу через свой контакт; связи `contact_groups` — через контакт
  и группу (оба одного владельца), отдельная колонка им не нужна.
- Чтения (`page.tsx`, `contacts/[id]/page.tsx`, `groups/page.tsx`,
  `keep-in-touch.ts`) добавляют `where owner_id = :userId`. Карточка и действия по
  номеру записи сверяют владельца: чужой контакт → `notFound()` («Контакт не
  найден»); чужую заметку/группу действие отвергает.
- Уникальность имени группы переезжает с глобальной на **в пределах владельца**:
  функциональный индекс становится `(owner_id, translate(lower(name),'ё','е'))`.
  Помощник «найти-или-создать группу» ищет среди групп текущего пользователя.
- Новый пользователь: его `where owner_id = :userId` даёт пусто → показываем
  подсказку «Добавь первый контакт».

### Перенос существующих данных на владельца `OWNER_EMAIL`

Классический приём «расширить → заполнить → сузить», весь внутри одного шага
миграции на выкатке (до старта нового образа), в фиксированном порядке:

1. **Расширить:** создать таблицы Better Auth; добавить `owner_id` как
   **необязательную** (nullable) колонку к `contacts` и `groups`; сменить
   уникальный индекс групп на `(owner_id, имя)`.
2. **Заполнить:** завести пользователя с почтой `OWNER_EMAIL` (если его ещё нет) и
   проставить его владельцем всем записям, у которых владелец пуст.
3. **Сузить:** сделать `owner_id` обязательной (NOT NULL).

- Порядок между шагами гарантируется так: миграционный раннер (`src/db/migrate.ts`/
  `.mjs`) перед применением миграций кладёт почту в настройку сессии Postgres
  (`select set_config('app.owner_email', $OWNER_EMAIL, false)`), а шаг 2 —
  ** handwritten** миграция, которая берёт её через `current_setting('app.owner_email')`,
  делает `INSERT ... ON CONFLICT (email) DO NOTHING` в `user` и `UPDATE ... WHERE
  owner_id IS NULL`. Шаг 3 идёт отдельным ALTER после него в том же прогоне. Так
  `drizzle-kit generate` остаётся источником структуры, а значение почты не попадает
  в git.
- Шаг идемпотентен: после первого прогона пустых `owner_id` нет, повторный деплой
  ничего не меняет. Демо-данные (`src/db/seed.ts`) создаются сразу с `owner_id`
  владельца, читая тот же `OWNER_EMAIL`.
- Почему пред-создаём пользователя, а не ждём первый вход: NOT NULL нужен сразу, а
  данные уже есть. Когда владелец позже войдёт по той же почте, Better Auth
  сопоставит его с существующим `user` по уникальному `email` — дубля не будет
  (`email_verified` ставим `true`).

### Автотесты входа

- Mailpit добавляется в `docker-compose.yml` (локально) и сервисом в e2e-джобу CI;
  у Mailpit есть HTTP-API, из которого тест достаёт ссылку входа.
- Помощник `e2e/support/login.ts`: запросить ссылку по почте → получить письмо из
  Mailpit API → перейти по ссылке → пользователь внутри.
- Новый `e2e/login.spec.ts` проверяет критерий из требований: A вошёл и добавил
  контакт; B вошёл — контакта A нет в списке и поиске, прямая ссылка на контакт A
  даёт «Контакт не найден».
- `e2e/main-scenario.spec.ts` остаётся отдельным, но его первый шаг теперь —
  вход через помощник (без входа приложение закрыто). Уникальные почты на прогон,
  чистка созданных строк в `afterAll`, как уже заведено.

## Risks / Trade-offs

- [Поведение `expiresIn`/одноразовости зависит от версии Better Auth] → версия
  закреплена (`1.7.18`); при реализации проверяем ручным/авто-тестом, что срок 15
  минут и повтор ссылки не входит.
- [Гашение старых ссылок не гарантировано плагином] → явно удаляем прежние
  невостребованные `verification` для почты в `sendMagicLink`.
- [Лимит «на почту» не встроен] → явный подсчёт за 10-минутное окно; встроенный
  лимитер оставляем грубой защитой.
- [Пред-созданный владелец может разойтись с логикой Better Auth при первом входе]
  → сопоставление по уникальному `email`, `email_verified=true`; проверяем, что
  первый вход не плодит второго пользователя.
- [Порядок «заполнить перед NOT NULL» в одном прогоне миграций] → значение почты
  через `set_config`/`current_setting`, backfill — handwritten миграцией строго
  перед ALTER NOT NULL; шаг идемпотентен.
- [Cross-origin/базовый URL (история PR #11)] → `BETTER_AUTH_URL`/`trustedOrigins`
  из настроек; локально и на сервере задаём явно.
- [DNS и домен отправителя для Resend] → владелец настраивает DNS домена
  `mail.crm.<домен>` и кладёт `RESEND_API_KEY` на сервер (действие человека);
  адрес отправителя — настройка `MAIL_FROM`, значение по умолчанию
  `noreply@mail.crm.dobrymaxx.ru`.
- [Секреты] → `BETTER_AUTH_SECRET`, `RESEND_API_KEY`, `OWNER_EMAIL` только в
  `.env`/`deploy/.env`; в git — ключи без значений в `.env.example`.

## Migration Plan

- **Выкатка.** Как и сейчас: бэкап базы → шаг миграции (расширить → заполнить →
  сузить, см. выше) одним one-shot до старта образа → новый образ → smoke
  `/health`. Падение любого шага миграции не даёт образу стартовать.
- **CI.** В e2e-джобу добавить сервис Mailpit и переменные `OWNER_EMAIL`,
  `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_*`, `MAIL_FROM`; шаг `pnpm
  db:migrate` на пустой базе просто создаёт пользователя-владельца (безвредно).
- **Откат.** Только вместе: база из бэкапа, снятого до выкатки, и прошлая версия
  приложения (как сказано в требованиях). Автоотката нет, запускает человек.
- **Env.** Новые ключи добавляются в `.env.example` и `deploy/.env.example`.
  Реальные значения (включая `OWNER_EMAIL=idmaksim@gmail.com`) владелец вносит в
  `.env` локально и `deploy/.env` на сервере; агент эти файлы не читает и не пишет,
  а подсказывает, какие строки добавить.

## Open Questions

- Значение `session.updateAge` (как часто продлевать сессию при активности) — взят
  разумный дефолт «раз в сутки»; можно изменить позже, на требования и задачи это
  не влияет.
